## Choices where the spec left room
1. **`TextFolding` has only `transliterate`.** `:core:search` may not see `:core:platform-api` (§2.1), so the
   pure steps of `fold` live in `:core:search`; the VM passes `textFolding::transliterate` as a `Transliterate`.
   `FakeTextFolding` (in `:testing:fakes`) is table-based because ICU4J may not sit on a runtime classpath;
   the ICU4J stand-in of T-SEARCH-04/05 lives in `:core:search` tests.
2. **Fold details.** Separators are whitespace and `-_.·'’` only; other symbols are kept. Non-Latin = a folded
   letter outside a–z; transliteration is run for those labels only, cached per label across rebuilds.
   Japanese voiced marks are combining marks after NFKD, so "ビ" folds to "ヒ" for queries and labels alike.
3. **Tiers.** T3 = a word start after the first (the first is T2); T4 needs ≥ 2 words and a query ≥ 2 chars;
   a transliterated T6 match scores 0 (still a result). An app's score is its best form.
4. **Tie order** = the assembled list's order (already ICU collation), so the VM needs no comparator; hidden
   apps come after shown ones when everything else is equal. `SearchIndex.build` still takes an optional comparator.
5. **Usage boost** from `LaunchLogRepository.counts()`, rebuilt on every log change; empty while
   `launch_log_paused`. Recents ask for 16 keys and keep 8 after dropping missing apps and (setting off) hidden ones.
6. **Layout (user-visible).** The field sits at the **top** of the search layer ("the field rises from the pill
   position"); results below it in rank order, bottom-padded by the IME inset; home/list underneath fade to
   0.3 α and leave the accessibility tree. Recents get a "Recent apps" heading. No result cap.
7. **After a launch** search clears and returns to its **origin** (list or rest); Home from any search goes to
   HOME_REST. Esc closes; Enter with no app results but a store row hands off to the store.
8. **Back.** The IME consumes the first Back itself. With an empty query, the IME closing (not caused by a
   results drag) closes search, which gives "one Back closes". `PredictiveBackHandler` fades the layer (up to
   70 %) and restores it on cancel.
9. **Hardware keys.** Root `onKeyEvent` on `HomeRoute` (keys bubbling from a focused row) plus a
   `HomeActivity.onKeyDown` fallback when nothing is focused. Printable = no Ctrl/Alt/Meta, not whitespace or
   control; digits included. Tab (rest → list), Esc (list → rest) and Ctrl+, (settings) are handled too;
   Menu/Shift+F10 (sheet) waits for M3.
10. **IME flags.** `ImeAction.Go`, autocorrect off, no capitalisation; `IME_FLAG_NO_PERSONALIZED_LEARNING` is
    added through `InterceptPlatformTextInput` (experimental Compose API).
11. **Store hand-off** needs a `<queries>` entry (`VIEW` + scheme `market`) so the handler is visible on API 30+.
    It is not in ANDROID_PLATFORM §22's skeleton; no permission changes (T-CI-01 unchanged).
12. **FR-HOME-05** "Home press opens search" is honoured already (cheap); its device test T-HOME-10 is M3.
13. Search query lives in the VM (and the field's `TextFieldValue` in composition); the activity is not
    recreated on config changes, so no `SavedStateHandle` yet.

14. **IME show retry: ANDROID_PLATFORM §14 as written ("retry once after a frame", Inferred).** A bounded
    retry loop (`show()` every 100 ms for up to ~1 s while the IME was not visible) was tried in 63f118d and
    reverted. It was a deviation from §14, motivated by a misread API 26 CI failure. That failure was a "Back
    must close search" wait, not the IME failing to appear. Evidence against the loop:
    - On CI run 41569832788 (API 36), the IME was hidden by the user's Back at 22.98 s. The loop, still running
      because Compose had not yet reported the IME visible, issued `show()` again at 24.06 s. The keyboard came
      back and search did not close (T-SEARCH-10's last step).
    - On API 26, the IME restarted its input view after the first Back, the same re-show.
    A user pressing Back during the first second would see the keyboard return.
16. **"One Back closes" keys off the IME *target*, not `isImeVisible`.** The empty-query close (item 8)
    used to fire on Compose's `WindowInsets.isImeVisible` going true → false. Compose 1.11 updates
    `isImeVisible` only when the IME insets animation ends; `imeAnimationTarget` updates as soon as the insets
    change. On CI run 41571533617 (API 36), Back hid the IME (`onHidden` 19.93 s) but the client hide
    animation only finished on a 10 s timeout (`PHASE_CLIENT_ANIMATION_CANCEL … STATUS_TIMEOUT` at 29.41 s).
    Search stayed open far past T-SEARCH-10's 3 s. A Back during the show animation could also be missed: Compose
    never saw "visible". This is a user-facing bug on slow devices (FR-SEARCH Back semantics), not a test
    artefact. Gesture back takes the same path because the IME, not the app, consumes the first Back.
15. **Device-test harness (`SearchDeviceTest`).** On the full Google emulator images a system "isn't
    responding" dialog takes input focus over every app. CI evidence: `mCurrentFocus=Window{… Application Not
    Responding: com.android.systemui}` on API 36; the Pixel Launcher on API 34. `DeviceStateRule` makes Strata
    the default home, sets `hide_error_dialogs=1` for the test and closes such a dialog. Both changes are
    restored afterwards. `UiAutomation.executeShellCommand` is not a shell (no pipes), and Android's ICU regex
    needs `}` escaped. A System UI dialog is answered **Wait**, never "Close app". CI run 41664919322 (API 36,
    job 126018053857): the harness closed "System UI isn't responding" at 07.91 s. System UI restarted
    (`StatusBar` input channels disposed at 10.62 s, new process on the lockscreen scene at 13.18 s), our
    activity was paused and stopped (12.12 s, 12.30 s), and T-SEARCH-02 failed with "No compose hierarchies".
    In the next test, T-SEARCH-10's first IME wait failed (line 105, before any Back). The IME show requested at
    40.84 s ended `setFinished at PHASE_WM_GET_CONTROL_WITH_LEASH with STATUS_TIMEOUT` at 51.05 s. The
    product's close logic was never reached. The same run passed on API 26 and 34.
    `DeviceStateRule` also sets the window, transition and animator scales to 0 for the test and restores them
    afterwards. CI run 41667894220 (API 34, job 126028061374) failed T-SEARCH-10's last wait (line 119, "Condition
    still not satisfied after 3000 ms"). Back was pressed at 50.68 s, Gboard took it at 50.86 s, but
    `ImeTracker … onHidden` came only at 51.55 s. `FrameTracker` then force-finished the IME insets animation
    on timeout (52.78 s), with the app drawing at roughly 1–3 fps (`app_time_stats avg` 300–1000 ms). That left
    about 2 s of the 3 s budget for recompose, close and the test's re-check. There are no app logs to tell a slow
    close from a missed one. Earlier runs on these emulators fit the same pattern: multi-second Davey frames, IME
    animations hitting the 10 s timeout (item 16), and ANR dialogs. With animations at 0 the IME show and hide
    apply at once, so Back timing no longer depends on emulator load. The close logic is unchanged and still
    keys off the IME target state. Cost: CI no longer exercises the slow-animation case from item 16. That case
    is covered by reasoning only (and on the owner's phone, where animations are on).
    CI run 41670711767 (API 34, job 126038001386) ran no tests: `:app:api34Setup` failed on a truncated
    system-image download ("Archive is not a ZIP archive", `InstallFailedException`). `run-gmd.sh` did not
    recognise this as infrastructure, so it did not retry. It now does, and clears the SDK's partial downloads
    before the retry.
    For triage, debug builds log every close decision as `Strata/SearchClose` (`HomeActivity.searchCloseLog`).
    Each line gives the IME observation and its source, the tracker result with query-blank and drag flags,
    back-handler closes and `onClose`. Booleans only, never the query; nothing is logged in release.
    Animations at 0 do not starve `imeAnimationTarget`. Compose 1.11.4's `InsetsListener.onApplyWindowInsets`
    calls `updateImeAnimationTarget` on every dispatch, whatever `prepared`/`runningAnimation` say. Only
    `update()` (`isImeVisible` and the inset values) waits for `onEnd`. `onEnd` checks the animation's declared
    `durationMillis`, which the duration scale does not change.
17. **Below API 30, "one Back closes" reads the root view's IME state, not Compose's.** CI run 41660558821
    (job 126002300857, GMD API 26 google image, T-SEARCH-10's last step; also run 41576277117, other runs
    pass): search reopened with an empty query, Back at 33.51 s hid Gboard, the test's
    `ViewCompat.getRootWindowInsets(…).isVisible(ime())` reported it hidden, our window held focus and was
    resumed, yet search stayed open 3 s later. On API 26 Gboard consumes that Back, so the IME-hide edge is the
    only close path, and the edge never reached Compose. Cause, from source (Confirmed for the code path;
    which delivery order a given run takes is Inferred):
    - API 26 `ViewRootImpl.performTraversals` (oreo-release), when a relayout returns new content *and*
      visible insets, calls `dispatchApplyInsets(host)` *before* `mAttachInfo.mVisibleInsets.set(…)`. Only a
      change that arrived earlier via `MSG_RESIZED` is stored before dispatch (the `layoutRequested` block), so
      the result depends on timing.
    - androidx.core 1.18 `WindowInsetsCompat.Impl20` (API < 30) computes the IME inset as the system-window
      bottom if it exceeds the stable bottom (adjustResize), else the root view's *visible* insets read by
      reflection when the insets are wrapped. Under edge-to-edge, after the hide the system-window bottom equals
      the stable bottom (nav bar), so the IME inset comes from the stale visible insets: "IME up".
    - Compose foundation-layout 1.11.4 `InsetsListener.onApplyWindowInsets` sets `imeAnimationTarget` from every
      dispatch (and `isImeVisible` from the same insets after the compat animation), so *both* stay "visible"
      until some later dispatch, which may never come. The test's on-demand read re-reads the visible insets
      and sees the truth. Not the cause: the compat animation path (`imeAnimationTarget` does not depend on it)
      or a stale edge across a reopen (`SearchScreen` leaves composition on close, so its edge state resets).
    Fix: `rememberImeShownForClose` (`ImeBackClose.kt`) uses, below API 30, `ViewCompat.getRootWindowInsets`
    re-read on every pre-draw; API 30+ keeps `imeAnimationTarget` (item 16). Pre-draw, not global layout: in
    the stale case content insets changed too, so `performMeasure` → `performLayout` → `dispatchOnGlobalLayout`
    does run after the visible insets are stored, but a later visible-insets-only change neither re-dispatches
    insets nor forces a layout (the measure gate is size/`contentInsetsChanged`/config), whereas
    `dispatchOnPreDraw` runs on every traversal. The listener writes only real changes (no loop). OR-ing
    Compose's signals would not help: both are stale. The edge logic is `ImeCloseTracker` (U,
    `ImeCloseTrackerTest`); it owns the results-drag mark and clears it on any "visible" observation, so a drag
    while the IME was already hidden cannot swallow a later empty-query Back. It only reads IME state, never
    shows the IME (item 14).
